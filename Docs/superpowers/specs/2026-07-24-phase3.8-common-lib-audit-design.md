# Phase 3.8: `lib/common.lib.php` Audit — Design

**Date:** 2026-07-24
**Status:** Approved
**Scope:** Produce an audit deliverable only. No changes to `lib/common.lib.php` or any of its callers in this phase.

## Context

`lib/common.lib.php` is 5,488 lines / 111 functions and is the single largest untouched piece of the modernization roadmap ([[project-modernization]]). Per `Docs/superpowers/specs/2026-07-21-phase3-sequencing-strategies.md`, it contains 169 of the project's 189 cataloged SQL-injection vulnerabilities (163 raw `sprintf()`-into-SQL, 5 discarded-return `mysqli_real_escape_string()` calls per `Docs/SQLi Remediation - mysqli_real_escape_string Audit.md`). It's loaded unconditionally by `site/bootstrap.php` (i.e. on essentially every legacy page render) plus directly by the self-bootstrapping side doors (`update.php`, `handle.php`, `setup.php`, `qr.php`). Modern code has exactly two sanctioned entry points into it today: `src/Domain/Entry/Adapter/LegacyQueryAdapter.php` (wraps `limit_subcategory()`) and `RegistrationService.php` (wraps `open_or_closed()`) — `LegacyQueryAdapter`'s own docblock states the intended rule ("no direct calls to common.lib.php outside this class") that the still-stubbed `NoLegacyReferenceOutsideLegacyRule` PHPStan rule would enforce once implemented.

The sequencing doc's own Phase 3.8 line reads: *"Audit; delete `lib/common.lib.php` if all callers migrated, or leave as deprecated legacy-only."* No call-graph analysis has ever been done against this file — this phase produces one.

## Deliverable

One new document: `Docs/PHASE_3.8_COMMON_LIB_AUDIT.md`, following the structure and citation style already established by `Docs/PHASE_3_TRUST_AUDIT.md` and `Docs/SQLi Remediation - mysqli_real_escape_string Audit.md`.

### 1. Scope & methodology section

States plainly: caller counts are from repo-wide static `grep` for each function name (excluding `vendor/`, `.worktrees/`, `.phpstan.cache/`), cross-referenced against the SQLi audit's flagged line numbers. Explicit caveat: static grep will not catch dynamic dispatch (variable function names, `call_user_func`, etc.) — none is known to exist in this file today, but the caveat is stated rather than assumed away.

### 2. Master table

One row per function (all 111), columns:
- Function name + line range
- Caller count, split into: legacy callers (sections/admin/output/includes), modern callers (`src/`), test callers (Unit/Approval/Integration)
- SQLi-flagged (Y/N + line citation, from the existing SQLi audit)
- Test coverage (which test file, if any — "none" is a valid and informative answer)
- Classification: one of `dead-code candidate (unverified)`, `keep-as-legacy-only`, `extraction candidate`, `superseded by src/Domain equivalent`

### 3. Narrative deep-dive

Prose detail on the ~15–20 functions that are either SQLi-flagged or have the highest caller counts — same depth/style as the SQLi audit's per-file breakdown, explaining *why* each is classified the way it is.

### 4. Recommendation section

Directly answers Phase 3.8's original question, broken into three buckets rather than one blanket verdict:
- **Confirmed-dead candidates** — zero static call sites, named as candidates for a small standalone future cleanup PR (not deleted in this phase).
- **Extraction-worthy** — high call count and/or SQLi-flagged, recommended for a future phase's targeted extraction (in the shape `LegacyQueryAdapter` already established).
- **Legacy-only-forever** — e.g. one-time migration/setup helpers not worth ever moving into `src/`.

Expected top-line answer: the file cannot be deleted yet (site/bootstrap.php and multiple side doors still require it unconditionally), so this phase's output is the triage, not the deletion.

## Out of scope for this phase

- Any code change to `lib/common.lib.php`, its callers, or `LegacyQueryAdapter`.
- Empirical (curl-based) verification of dead-code candidates — they're reported as unverified candidates only, consistent with `config/access_policy.php`'s own audit note that full empirical verification is a separate, deliberate pass.
- Deciding *which* extraction-worthy functions get picked up next — that's a future phase's own brainstorm/plan.
